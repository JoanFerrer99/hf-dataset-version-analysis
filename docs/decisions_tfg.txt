TÍTOL
-----
"How do HuggingFace Datasets Change? An Automated Pipeline for Version Analysis"

DESCRIPCIÓ (inscripció FIB, màx. 500 caràcters)
------------------------------------------------
Aquest treball té com a objectiu analitzar com canvien els datasets allotjats
al repositori de codi obert Hugging Face entre les seves versions successives.
Per assolir aquest objectiu, es dissenyarà i implementarà un pipeline
automatitzat que, mitjançant l'API pública de HF, permeti identificar els
datasets amb múltiples versions, extreure'n les diferències rellevants entre
versions consecutives i classificar el tipus de canvi produït.

OBJECTIUS ESPECÍFICS (OE) — ESTAT ACTUAL
------------------------------------------
OE1. Identificar de manera automàtica quants datasets de HuggingFace tenen
     múltiples versions detectables, i quina proporció de la població total
     representen. [Fase 0 — Filtratge previ i mostreig]
     ESTAT: ✅ Pràcticament tancat. Pipeline complet i validat (vegeu Bloc 2,
     M-02, i Bloc 6). Proporció d'elegibles observada: ~0.6% (execució de
     referència `eligibility_report_2000_3.csv`, N≈979.480).

OE2. Dissenyar un pipeline ETL que extregui, per a cada dataset elegible,
     les diferències entre versions consecutives de forma automatitzada.
     [Fase 1 — Extracció; Fase 2 — Transformació]
     ESTAT: 🔲 No iniciat. Depèn de OE1 (llista d'elegibles ja disponible).

OE3. Definir i implementar criteris de classificació que distingeixin canvis
     que afecten el contingut o l'esquema de les dades (canvis substantius /
     "breaking") dels canvis que afecten només metadades o documentació.
     [Fase 2 — Classificació; Fase 3 — Validació]
     ESTAT: 🔲 No iniciat pel que fa a la taxonomia de 15 codis (Fase 2),
     però el risc tècnic clau que la bloquejava (R-01, accés a la llista de
     fitxers per commit) ja està resolt (vegeu Bloc 5).

OE4. Avaluar la cobertura i fiabilitat del pipeline sobre la població
     elegible completa o una mostra estratificada si la mida ho requereix.
     [Fase 3 — Validació i anàlisi descriptiva]
     ESTAT: 🔲 No iniciat pel que fa a l'anàlisi final, però ja s'ha fet una
     primera validació de fiabilitat de la Fase 0 (US-108): precisió
     automàtica del criteri d'elegibilitat millorada de 38.5% a 100% sobre
     l'execució de referència, després d'identificar i corregir un patró
     sistemàtic de falsos positius (vegeu M-02 i R-04).

DECISIÓ M-01: Metodologia de mostreig
Data: juny 2026
Responsable: Joan + Director
Estat: ✅ Implementat i sense canvis

Decisió: Reservoir sampling (algorisme R de Vitter) sobre TOTA la població
de datasets de HF, sense ordenar per popularitat.

Raonament: Ordenar per popularitat introduiria un biaix a l'alça en la
proporció d'elegibles (els datasets populars tendeixen a tenir més versions
i manteniment). Per estimar correctament la mida de la població elegible
total, cal que cada dataset tingui igual probabilitat de ser seleccionat
(p = sample_size / N, on N és la mida total de la població).

Referència: Paper "Lessons Learned from Mining the Hugging Face Repository"
(Castaño et al., WSESE 2024), secció 3.2 — Stratified Sampling.

Alternativa descartada: Ordenació per downloads/likes (biaix de popularitat).
Alternativa futura: Si la població elegible és gran, aplicar estratificació
per domini + quartil de versions + quartil de popularitat. DECIDIT (vegeu
A-01 actualitzada): NO ha calgut, la proporció observada (~0.6-1.37% segons
l'execució) és molt per sota del llindar del 5% que hauria activat aquesta
alternativa.

Implementació: `iter_all_dataset_ids()` genera ids de tota la població
(~980K) sense materialitzar-la a memòria, amb `expand=["disabled"]` per
minimitzar la transferència de dades. `reservoir_sample_dataset_ids()`
guarda NOMÉS strings (ids) al reservori, mai l'objecte `DatasetInfo`
complet — requisit explícit del director per evitar problemes de memòria.


DECISIÓ M-02: Criteri d'elegibilitat d'un dataset
Data: juny 2026 (revisada substancialment: juliol-agost 2026)
Responsable: Joan + Director
Estat: ✅ Implementat, validat empíricament (US-108) i corregit

Versió ACTUAL del criteri (post-validació, substitueix la versió original
de juny 2026 descrita més avall):

  Criteri A — Versionat explícit: >= 2 tags de Git I >= 2 commits
              substantius associats als tags (evita comptar tags "buits"
              sense canvi real de dataset). NO exigeix cap dispersió
              temporal entre els tags: la presència de >=2 tags ja és un
              senyal deliberat de versionat pel mantenidor.

  Criteri B (fallback) — >= 2 branches I >= 2 commits substantius
              SEPARATS EN EL TEMPS per almenys `MIN_SUBSTANTIVE_GAP_HOURS`
              (actualment 6 hores, entre el commit substantiu més antic i
              el més recent).

  Un commit es considera "substantiu" (per a tots dos criteris) si TOCA
  REALMENT algun fitxer de dades, no purament de metadades/documentació.
  Es determina per INSPECCIÓ REAL dels fitxers afectats pel commit (clonatge
  "bare" local + `git show --name-status`, vegeu R-01 més avall), amb
  fallback a una heurística de títol només si el clonatge falla.

Versió ORIGINAL (juny 2026, per registre històric):
  Criteri A — >= 2 tags de Git (sense verificar cap commit substantiu).
  Criteri B — >= 2 commits el títol dels quals no és purament documental.
  (Sense requisit de dispersió temporal, sense inspecció real de fitxers.)

CANVIS RESPECTE A LA VERSIÓ ORIGINAL i per què:

  1. Criteri A ara exigeix també >=2 commits substantius (no només tags):
     cobreix el cas (improbable però possible) de tags "buits" sense canvi
     real associat.

  2. Criteri B ara exigeix dispersió temporal mínima entre commits
     substantius: la VALIDACIÓ MANUAL de US-108 (vegeu més avall) va trobar
     que el Criteri B original tenia una precisió de només 20% (2/10) sobre
     la mostra de referència. La causa identificada: eines d'exportació
     automàtica de dades (p.e. LeRobot, per a datasets de robòtica) generen
     desenes de commits en una única sessió de pujada de segons/minuts
     (`"Upload folder using huggingface_hub"`, `"Delete folder ..."`); cada
     commit individual passa l'heurística de títol, però el conjunt
     representa UNA sola versió, no múltiples. Exigir que els commits
     substantius estiguin repartits en el temps (no en una sola sessió)
     elimina la major part d'aquest patró de fals positiu.

  3. Detecció real de fitxers en lloc de l'heurística de títol pura
     (RISC R-01, ara resolt): en lloc de confiar només en el títol del
     commit (que pot ser genèric o enganyós), s'inspeccionen els fitxers
     REALS afectats via un clonatge "bare" del repositori (`git clone
     --bare --filter=blob:none`, sense descarregar el contingut real de
     les dades) i `git show --name-status <sha>` per cada commit — la
     mateixa tècnica que el paper dels LLM (Castaño et al. 2025, secció
     4.2.1) fa servir per al mateix problema exacte. Un fitxer es considera
     "substantiu" si NO és purament de metadades/documentació (README,
     .gitattributes, dataset_infos.json, LICENSE, CITATION.cff, .github/,
     etc.).

RESULTAT DE LA VALIDACIÓ (US-108):
  Sobre l'execució de referència neta (`eligibility_report_2000_3.csv`,
  N≈979.480, 12 elegibles), amb totes dues millores actives, la precisió
  automàtica ESTIMADA (basada en agrupació de commits substantius en
  "sessions de treball" — >=2 sessions clarament diferenciades pel Criteri
  B, el Criteri A és sempre considerat correcte pel seu propi disseny) va
  passar de 38.5% (5/13, execució original pre-correccions) a 100% (12/12).
  Aquesta xifra és una heurística automàtica de coherència, NO una
  confirmació manual definitiva — pendent de revisió final per Joan/el
  director (vegeu `docs/us108_validation_report.md`, regenerat
  automàticament a cada execució de `validate_eligible.py`).

  Limitació residual identificada explícitament (no "corregida" ajustant
  paràmetres a mida): datasets amb múltiples tags creats el mateix dia
  natural (separats només per hores) es classifiquen com a elegibles via
  Criteri A tot i que podrien representar una sola sessió de publicació
  esglaonada en lloc de versions independents — es deixa per a judici humà
  explícit en lloc de "resoldre's" silenciosament amb un llindar ad hoc.

Limitació coneguda (residual, no eliminable del tot): la detecció de
fitxers substantius per commit segueix sent una aproximació al concepte de
"versió real" — no inspecciona el CONTINGUT de les dades (només quins
fitxers han canviat), així que no distingeix, p.e., un canvi cosmètic d'un
fitxer de dades d'un canvi substancial del seu contingut. Aquesta limitació
és exactament l'abast de l'OE3/Fase 2 (taxonomia de canvis), encara no
iniciada.


DECISIÓ M-03: Definició de "canvi substantiu" (taxonomia)
Data: juny 2026
Responsable: Director
Estat: ⚠️ SUBSTITUÏDA per una versió formal i codificada (juliol 2026)

Aquesta secció descriu la taxonomia INFORMAL original (mapa mental, sense
codis), conservada per registre històric. HA ESTAT SUBSTITUÏDA per la
taxonomia formal codificada del paper del director (15 codis C100-C530 en
5 perspectives, amb ground truth validat sobre el dataset Census Income —
9 versions reals de HF), documentada a `docs/taiga/taxonomy.md`. Els canvis
principals respecte a aquesta versió informal:
  - "Arity" (dins de Columns Set) eliminada com a categoria classificable
    pròpia — ara es tracta com a "impacte", no com a tipus de canvi.
  - "Column Type → Categorical → Order" eliminada explícitament (informació
    no disponible al propi dataset).
  - "Cardinality" (dins de Rows Set) eliminada com a categoria pròpia.
  - "Target → Concept drift / Balance" NO són codis nous: són
    interpretacions de C520/C530 quan la columna afectada és el target
    del pipeline (la taxonomia classifica el dataset, no l'ús que se'n fa).

Base històrica (mapa mental original, ja substituït):

  Dataset changes
  ├── Metadata
  │     (source, licensing, file format, field delimiter, split train/test,
  │      temporal characteristics)
  ├── Columns Set
  │   ├── Column → Order / Rename / Add / Remove
  │   └── Arity
  ├── Column Type
  │   ├── Categorical → Type / Values / Order
  │   └── Numerical   → Type / Values
  ├── Rows Set
  │   ├── Row   → Order / Change ID / Add / Remove
  │   └── Cardinality
  └── Data Characteristics
      ├── Features → Missings / Correlations / Distribution
      └── Target   → Concept drift / Balance

Taxonomia formal ACTUAL (15 codis, `docs/taiga/taxonomy.md`):
  C100 Metadata | C210 Columns order | C221 Add column | C222 Remove column
  | C223 Rename column | C311 Categorical col. type | C312 Categorical col.
  values | C321 Numerical col. type | C322 Numerical col. values | C410 Rows
  order | C421 Add row | C422 Remove row | C510 Missings | C520 Correlation
  | C530 Data distribution

Decisió d'abast encara PENDENT (US-303, vegeu "Pròximes decisions"):
detectar les 15 categories completes (requereix contingut real de les
dades) o només les 7 detectables per esquema/metadades sense descarregar
contingut (C100, C210, C221, C222, C223, C311, C321).

Aquesta taxonomia és la base per al classificador automàtic (Fase 2, OE3),
encara no iniciada.


DECISIÓ M-04 (NOVA): Detecció de fitxers substantius — de denylist pura a
                      allowlist + prefix de ruta
Data: agost 2026
Responsable: Joan
Estat: ✅ Implementat i validat empíricament

Problema: `is_substantive_path()` (introduïda a US-302, M-02) determinava
si un fitxer canviat per un commit era "substantiu" amb una única llista
negra de noms exactes (`NON_SUBSTANTIVE_FILES`) — tot el que NO hi era
explícitament es considerava substantiu per defecte. Aquest disseny és
estructuralment incapaç de ser complet: un denylist enumera exclusions
d'un espai obert (qualsevol nom de fitxer possible), així que sempre hi
ha convencions noves que se n'escapen (`CARD.md`, `pyproject.toml`,
`changelog.json`, etc.) i es compten erròniament com a canvis substantius.

Hipòtesi inicial explorada i DESCARTADA amb evidència: fer servir la MIDA
del fitxer com a desempat per a extensions ambigües (`.json`/`.txt`).
Es va provar de llegir la mida real via el punter Git-LFS (el "blob" que
git guarda localment per a un fitxer LFS és només ~130 bytes de text amb
un camp `size:` — llegir-lo no trenca la garantia de "mai descarregar
dades reals" del clonatge bare, US-302).

Calibratge empíric: 4 datasets reals clonats i inspeccionats
(`AG42/lerobot_dataset_try1`, `villekuosmanen/close_shoebox`,
`unitreerobotics/G1_Dex3_ObjectPlacement_Dataset`,
`AndreaBozzo/ceres-open-data-index`). RESULTAT: la mida NO separa bé
metadada de dades reals — un fitxer de metadades pot ser MÉS GRAN que un
fitxer de dades genuí del mateix dataset:
  - `meta/episodes_stats.jsonl` (villekuosmanen): 393KB — metadada, més
    gran que la majoria dels `data/chunk-*/episode_*.parquet` del mateix
    dataset.
  - `meta/episodes/chunk-000/file-000.parquet` (unitreerobotics): 482KB —
    metadada, tot i l'extensió `.parquet` (normalment fiable com a "dades
    reals").
  - `changelog.json` (AndreaBozzo): 62KB — metadada (un canvi de registre).
El senyal que SÍ va separar-ho de forma consistent en els 4 datasets: el
PREFIX DE LA RUTA (`meta/`/`meta_data/` conté sempre metadada,
`data/`/`videos/` sempre contingut real).

Decisió final (implementada a `eligibility_scan.py`): ordre de decisió en
"defensa en profunditat" dins `is_substantive_path()`:
  1. Prefix de ruta a `NON_SUBSTANTIVE_PATH_PREFIXES` (`meta/`,
     `meta_data/`, `.github/`) → NO substantiu, INDEPENDENTMENT de
     l'extensió (comprovat abans que l'extensió a propòsit).
  2. Nom exacte a `NON_SUBSTANTIVE_FILES`, o extensió a
     `NON_SUBSTANTIVE_EXTENSIONS` (`.md`, `.yml`, `.yaml`, `.toml`,
     `.cfg`, `.ini`, `.lock` — generalitzat per extensió, no només noms
     exactes com abans) → NO substantiu.
  3. Extensió a `SUBSTANTIVE_DATA_EXTENSIONS` (parquet, csv, arrow,
     tensors, multimèdia, arxius) → substantiu.
  4. Qualsevol altre cas (p.e. `.json`/`.txt` fora de `meta/`, o una
     extensió no prevista) → substantiu per defecte (fail-open), però
     REGISTRAT (`log.debug`) per revisió i ampliació futura de les
     llistes amb dades reals, en lloc d'endevinar-les.

Validat amb 87 tests unitaris (inclosos els casos límit del calibratge:
`.parquet` sota `meta/` vs sota `data/`).

Lliçó metodològica general (aplicable a qualsevol decisió de disseny
futura del pipeline): abans d'implementar una heurística basada en una
intuïció (aquí, "més gran = més probable que sigui substantiu"), calibrar
amb dades reals. La intuïció inicial es va descartar amb evidència
concreta en lloc de forçar-la a "funcionar" ajustant un llindar a mida.

DECISIÓ T-02: Estratègia de paral·lelització i gestió d'errors
Data: juny 2026 (ampliada: juliol 2026)
Estat: ✅ Implementat i validat empíricament

  Fase de mostreig (reservoir sampling): seqüencial. El sampling és un
  procés inherentment seqüencial (cal veure cada element en ordre).

  Fase de classificació: paral·lel amb ThreadPoolExecutor (I/O-bound,
  no CPU-bound, per tant threads > multiprocessing).

  Nombre de threads per defecte: 4. Ajustable via --threads.

  Gestió de rate limiting (HTTP 429) — AMPLIADA respecte a la decisió
  original ("sleep implícit"): implementat `errors.with_retry()` amb
  backoff exponencial + jitter, després d'avaluar 4 alternatives (cap
  reintent / espera fixa / backoff sense jitter / backoff amb jitter).
  Validat empíricament: taxa d'errors 429 reduïda d'~59% a ~0% en
  execucions reals. Els errors 403 (accés restringit/gated) es tracten
  per separat: NO es reintenten (condició permanent, no transitòria) i
  s'exclouen tant del numerador com del denominador de la proporció
  d'elegibles. Detall complet a `notebooks/errors.py` (docstring de
  disseny inclosa al mateix mòdul).

DECISIÓ T-04: Esquema en estrella (data warehouse)
Data: juny 2026
Estat: 🔲 Pendent (sense canvis, Fase 3 no iniciada)

Proposta inicial del professor. Esquema bàsic:

  Taula de fets: Change
    - dataset_id (FK → Dataset)
    - date_id (FK → DateOfChange)
    - kind_of_change_id (FK → KindOfChange)
    - age_days (atribut calculat: DateOfChange - CreationDate)

  Dimensions proposades:
    - Dataset (dataset_id, name, domain, license, num_downloads,
               creation_date, num_versions, ...)
    - DateOfChange (date_id, date, year, quarter, month)
    - KindOfChange (kind_id, category, subcategory, is_breaking,
                    taxonomy_level_1, taxonomy_level_2, taxonomy_level_3)

  La dimensió KindOfChange s'alineará directament amb la taxonomia FORMAL
  de 15 codis (Decisió M-03 actualitzada), no amb el mapa mental informal
  original.

  Pendent de decisió: PostgreSQL vs DuckDB com a motor (US-401, encara
  oberta).
  DuckDB és més adequat per a anàlisi local sense servidor (estil TFG);
  PostgreSQL és millor si es vol desplegar o escalar.

RISC R-01: Endpoint de llista de fitxers per commit
Detectat: juny 2026
Estat: ✅ RESOLT (juliol 2026)

L'API pública de HF no exposa de forma estable i documentada la llista
completa de fitxers modificats per commit via REST. CONFIRMAT
empíricament (juliol 2026): `GitCommitInfo` (`huggingface_hub==1.18.0`)
només exposa `commit_id`/`authors`/`created_at`/`title`/`message` — cap
camp de fitxers.

Resolució implementada: exactament l'alternativa prevista en aquest risc
—clonatge "bare" del repo (`git clone --bare --filter=blob:none`, sense
contingut real dels fitxers) + `git show --name-status <sha>` per commit,
com fa el paper dels LLM (Castaño et al. 2025, secció 4.2.1). Validat
empíricament: <1s i ~150KB per repositori de prova. Implementat a
`eligibility_scan.bare_clone`/`get_changed_files`/`determine_commit_
substantive`. Requereix `git` instal·lat al sistema/imatge (vegeu R-05).

Impacte final: ha permès substituir l'heurística de títol pel Criteri B
(M-02), millorant la precisió automàtica de 38.5% a 100% sobre l'execució
de referència (vegeu R-04).


RISC R-02: Rate limits de l'API de HF
Detectat: juny 2026
Estat: ✅ MITIGAT i validat empíricament (juny-juliol 2026)

L'API de HF té rate limits que varien amb el token. Implementat
`errors.with_retry()` amb backoff exponencial + jitter (4 alternatives
avaluades: cap reintent / espera fixa / backoff sense jitter / backoff amb
jitter — la quarta és la implementada). Validat en execucions reals: taxa
d'errors HTTP 429 reduïda d'~59% a ~0%. Els errors HTTP 403 (accés
restringit/gated) es tracten com a categoria separada, NO transitòria: no
es reintenten i s'exclouen del càlcul de la proporció d'elegibles.

Nota descartada explícitament: es va investigar la hipòtesi (suggerida en
un fòrum de HF) que el rol del token (read vs write) causava els errors
403; es va descartar amb evidència empírica (100% dels 403 capturats
coincideixen amb el patró "gated repo... not in authorized list", no amb
cap missatge de permisos/rol). Detall complet a `notebooks/errors.py`.


RISC R-03: Canvis a l'API de HF
Detectat: juny 2026
Estat: 🟡 VIGILAT (sense canvis, risc obert per naturalesa)

L'API de HF és activa i pot canviar. Tots els resultats s'han de guardar
amb timestamp. Si es torna a executar el pipeline mesos més tard, els
resultats no seran idèntics (la població de HF canvia constantment).
Mitigació: --seed per a reproduïbilitat del mostreig (quan es fixa), i
cada execució genera fitxers de sortida numerats (`run_id`) sense
sobreescriure execucions prèvies.


RISC R-04 (NOU): Falsos positius sistemàtics al Criteri B — patró LeRobot
Detectat: agost 2026 (validació manual US-108)
Estat: ✅ MITIGAT (vegeu M-02)

La validació manual de la mostra de referència (13 datasets elegibles,
execució original) va trobar que el Criteri B tenia una precisió de només
20% (2/10). Causa arrel identificada: eines d'exportació automàtica de
dades (p.e. LeRobot, format estàndard per a datasets de robòtica) generen
desenes de commits amb títols que passen trivialment l'heurística de
títol (`"Upload folder using huggingface_hub"`), tots dins d'una única
sessió de pujada de segons/minuts — representen UNA versió, no múltiples.

Mitigació implementada: exigir dispersió temporal mínima (actualment 6h)
entre els commits substantius del Criteri B, més la detecció real de
fitxers (R-01). Resultat: precisió automàtica 38.5% → 100% sobre
l'execució de referència neta. Limitació residual documentada
explícitament a M-02 (casos límit de tags creats el mateix dia natural),
deixada per a judici humà en lloc de "corregir-se" ajustant llindars a
mida dels casos observats.


RISC R-05 (NOU): Bug de desplegament — `git` no instal·lat a la imatge Docker
Detectat: agost 2026
Estat: ✅ RESOLT

La primera execució via Docker amb la millora de detecció real de fitxers
(R-01) es va beneficiar només de la millora de dispersió temporal (R-04):
la imatge Docker (`python:3.12-slim`) no tenia `git` instal·lat, així que
el clonatge fallava SILENCIOSAMENT per a TOTS els datasets i el pipeline
recorria sempre al fallback d'heurística de títol, sense cap avís visible
als logs.

Lliçó apresa i mitigació: 1) Corregit el `Dockerfile` (`apt-get install
git`). 2) `bare_clone()` ara registra un `log.error` (un sol cop per
procés, no un cop per dataset, per no inundar els logs) si `git` no és al
`PATH`, perquè aquest tipus de fallada de desplegament sigui detectable
immediatament als logs en comptes de requerir investigació manual
posterior. Confirmat amb una segona execució neta que la correcció
funciona.


RISC R-06 (NOU): Falsos positius del "push protection" de GitHub (secret scanning)
Detectat: juliol-agost 2026 (recurrent)
Estat: 🟡 VIGILAT (friction point conegut, no un risc real de seguretat)

Alguns noms de dataset de HF (generats automàticament per usuaris, p.e.
`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`) coincideixen per atzar amb el
patró d'un token d'accés de HF, i el "push protection" de GitHub bloqueja
el `git push` de fitxers `data/*.csv` que els contenen. CONFIRMAT en més
d'una ocasió que és sempre un fals positiu (nom de dataset, no una
credencial real) — mai s'ha trobat un secret real filtrat. Resolució:
seguir el flux oficial de GitHub (marcar "false positive" a la URL de
desbloqueig que proporciona l'error), MAI reescriure l'historial de git
ni esborrar dades reals per aquest motiu.
